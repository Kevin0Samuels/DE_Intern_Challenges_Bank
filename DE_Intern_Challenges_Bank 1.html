2. Script development

  1. Data loading: load all CSV files into DataFrames.
  2. Data cleaning: clean the data by handling missing values and correcting data types.
  3. Data processing:
    • Time adjustment: all timestamp values are in UTC. Convert them to local time based on the timezone provided on the table. If the timezone does not exist on that table, join with another table.
    • Join tables: merge the tables appropriately and make sure there are no duplicates.
    • Handling nulls: null values should not exist / should be removed.
    • String adjustment: apply initcap to string values, except the club name.
    • Source category: determine referral_source_category using the following logic: 
      CASE
  WHEN referral_source = 'User Sign Up'      THEN 'Online'
  WHEN referral_source = 'Draft Transaction' THEN 'Offline'
  WHEN referral_source = 'Lead'              THEN leads.source_category
END AS referral_source_category
  4. Basic business logic implementation: implement these rules to detect potential fraud in a new column named is_business_logic_valid (type: bool).

    Valid referral rewards

    Condition 1: valid if all of the following hold:

    1. The reward value is greater than 0.
    2. The referral status is "Berhasil" (Successful).
    3. The referral has a transaction ID.
    4. The transaction status for the referral is "PAID".
    5. The transaction type for the referral is "NEW".
    6. The transaction occurred after the referral was created.
    7. The transaction happened in the same month as the referral creation.
    8. The referrer's membership has not expired.
    9. The referrer's account is not deleted.
    10. The reward has been granted to the referee.

    Condition 2: valid if:

    1. The referral status is either "Menunggu" (Pending) or "Tidak Berhasil" (Failed).
    2. There is no reward value assigned.

    Invalid referral rewards

    Condition 1: invalid if the reward value is greater than 0 and the referral status is not "Berhasil".

    Condition 2: invalid if the reward value is greater than 0 and there is no transaction ID for the referral.

    Condition 3: invalid if:

    1. There is no reward value assigned.
    2. The referral has a transaction ID.
    3. The transaction status for the referral is "PAID".
    4. The transaction occurred after the referral was created.

    Condition 4: invalid if the referral status is "Berhasil" and the reward value is either null or 0.

    Condition 5: invalid if the transaction occurred before the referral was created.

    Finding any invalid business logic in these rules themselves is a plus.

  5. Output: generate a report/table in CSV format that indicates whether each referral reward is valid or invalid based on the business logic. The correct report has 46 rows. It includes these columns:

Stage 1 · Foundation · Requires: stage 0

Local CSV → PostgreSQL via Dockerized Airflow

Objective

Build a containerized Apache Airflow pipeline that ingests a local CSV file, applies basic validation, and loads the cleaned data into a PostgreSQL table. Pick your dataset from the dataset list. All DAGs, configs and documentation are committed to your own repository.

Why this task exists

This is the first of a two-part sequence. It is a scaled-down mirror of a real data platform (Airflow-orchestrated ingestion into a warehouse). Stage 2 reuses the same dataset but lands it in MinIO as Parquet instead of PostgreSQL. Doing both teaches the difference between a relational sink and an object-store / lakehouse sink.

By the end you should be comfortable with Airflow DAG authoring, containerizing a stack with Docker Compose, schema-driven CSV ingestion, secure credential handling, and clean commit conventions.

Definition of done

  • The Airflow DAG runs end to end: CSV → transform / validate → PostgreSQL table.
  • The environment is reproducible via Docker Compose.
  • Credentials (PostgreSQL host / user / password) are stored securely, never hardcoded.
  • The dataset's status (its analysis status in the dataset list) is recorded in the manifest and respected by the pipeline.
  • Code and docs are committed to your repo with clear run instructions.

Architecture and data flow

dataset list (download the CSV)
        |
        v
   local CSV ----> [ Airflow DAG, running in Docker ]
                     |             |            |
                  validate  ->  transform  ->  load
               (schema.yaml)    (clean)    (PostgresHook)
                                                |
                                                v
                                        PostgreSQL table

Everything (Airflow + PostgreSQL) runs locally via docker compose.

Stories

Deliverables, hints and acceptance criteria are guidance. Confirm the exact expectations with your mentor if in doubt.

Story 1: Prepare the dataset manifest, schema YAML and SQL DDL

Goal: formally describe the dataset before writing any pipeline code.

Deliverables: manifest.yaml, schema.yaml, ddl.sql.

Example schema.yaml:

dataset: example_dataset
primary_key: [id]
columns:
  - name: id
    type: integer
    nullable: false
  - name: client_name
    type: string
    nullable: false
  - name: amount
    type: decimal(12,2)
    nullable: true
  - name: created_at
    type: timestamp
    nullable: false

Acceptance: the schema matches the CSV header and types; ddl.sql creates the table without error; the manifest records the dataset status.

Story 2: Dockerized Airflow environment

Goal: a one-command local stack running Airflow + PostgreSQL.

Deliverables: docker-compose.yaml, .env.example.

Hints: base it on the official apache/airflow image; mount your dags/ folder; expose the Airflow UI on :8080; keep the target PostgreSQL as its own service; pull all connection values from .env (never commit real secrets).

Acceptance: docker compose up starts Airflow, the UI loads, and your DAG appears in the list.

Story 3: Airflow DAG to load the local CSV

Goal: a DAG that reads the CSV, validates it against schema.yaml, transforms/cleans it, and loads it into PostgreSQL.

Suggested tasks: read_csv → validate_schema (fail on mismatch) → transform → load_to_postgres (idempotent).

Hints: use PythonOperator + PostgresHook (or SQLAlchemy); pandas for read/clean; set catchup=False; respect the dataset status field; make reloads safe (truncate-then-load, or upsert on the primary key).

Acceptance: a full run populates the PostgreSQL table with the expected rows; re-running does not duplicate data; a deliberately malformed CSV makes the DAG fail at the validation step.

Story 4: Documentation and runbook

Goal: anyone can reproduce your pipeline from scratch.

Deliverable: README.md covering prerequisites, docker compose up, how to trigger the DAG, how to verify rows in PostgreSQL, and common troubleshooting.

Acceptance: a teammate with only Docker installed can follow the README end to end.

Tech stack and prerequisites

  • Docker and Docker Compose
  • Python 3.11+, Apache Airflow 2.x
  • PostgreSQL
  • pandas, PyYAML, a Postgres driver (psycopg2)
  • Your own Git repository

Getting started

  1. Create your repository and a stage-1-csv-to-postgres/ folder.
  2. Choose a dataset from the dataset list and download its CSV into your dataset folder.
  3. Story 1: write manifest.yaml, schema.yaml, ddl.sql.
  4. Story 2: write docker-compose.yaml and .env.example; bring the stack up.
  5. Story 3: write and run the DAG until the table loads cleanly.
  6. Story 4: write the README, then open a PR for review.

Conventions: no secrets in code (use .env / Airflow Connections), catchup=False, and no heavy top-level I/O in the DAG file.

Stage 2 · Foundation · Requires: stage 1 (same dataset)

Local CSV → MinIO Parquet Ingestion Pipeline

Objective

Build an Airflow-based pipeline that ingests a CSV file (dags/extraction/sample.csv), validates it against a schema contract, transforms it, and loads it into MinIO as partitioned Parquet.

Relationship to stage 1

This stage reuses the same dataset as stage 1 and keeps the same shape (ingest → validate → transform → load), but changes the destination from a relational database to an object store in Parquet format. It also raises the bar on validation: the schema contract must fail the DAG on mismatch, which is stricter than stage 1's basic validation.

Definition of done

  • End-to-end run: CSV (local) → validate → transform → Parquet in MinIO (server).
  • Schema contract enforced: the DAG fails if the CSV does not match.
  • Parquet files are stored in MinIO and browsable via the MinIO console.
  • The environment is reproducible via Docker Compose.
  • Code and docs are committed to your repo with run steps.

Architecture and data flow

dags/extraction/sample.csv  (same dataset as stage 1)
        |
        v
  [ Airflow DAG, running in Docker ]
     |                  |             |
  validate     ->   transform  ->  write Parquet
  (schema contract)   (clean)       (partitioned)
  FAIL on mismatch                     |
                                       v
                          MinIO bucket (S3-compatible)
                          browsable in MinIO console :9001

Airflow + MinIO both run locally via docker compose.

Repository layout

<your-repo>/
  stage-2-csv-to-minio/
    <dataset_name>/
      manifest.yaml          # dataset name, source, owner, status
      schema_contract.yaml   # the contract enforced at runtime
    dags/
      csv_to_parquet_minio.py
    docker-compose.yaml      # airflow + minio
    .env.example
    README.md

Stories

Deliverables, hints and acceptance criteria are guidance. Confirm the exact expectations with your mentor if in doubt.

Story 1: Dataset manifest and schema contract

Goal: define the dataset and a schema contract the pipeline will enforce.

Deliverables: manifest.yaml, schema_contract.yaml.

Hints: the contract specifies column names, types, nullability and, optionally, simple value rules. The DAG must reject and fail when the incoming CSV violates it. This is the core learning goal of this stage.

Acceptance: a conforming CSV passes; a CSV with a missing, renamed or mistyped column fails the contract check.

Story 2: Dockerized Airflow + MinIO environment

Goal: a one-command local stack running Airflow + MinIO.

Deliverables: docker-compose.yaml, .env.example.

Hints: add the minio/minio service (API :9000, console :9001); create the target bucket on startup (an init/mc container or a first-run task); feed the MinIO credentials and the Airflow connection from .env.

Acceptance: docker compose up brings up Airflow and the MinIO console; you can log into the console and see the (empty) target bucket.

Story 3: Airflow DAG: CSV → Parquet → MinIO

Goal: a DAG that reads the CSV, validates it against the contract, transforms it, and writes partitioned Parquet to MinIO.

Suggested tasks: read_csv → validate_contract (fail on mismatch) → transform → write_parquet_to_minio.

Hints: use pyarrow/pandas to write Parquet; partition by a sensible column (e.g. a date); talk to MinIO with the minio client, boto3 or s3fs (S3-compatible, custom endpoint_url); set catchup=False.

Acceptance: a full run produces partitioned .parquet objects visible in the MinIO console; a contract-violating CSV fails the DAG before anything is written.

Parquet and partitioning notes

  • Format: columnar Parquet, not CSV. This is the lakehouse-style sink.
  • Partitioning: lay files out as bucket/dataset/<partition_col>=value/part-*.parquet so the data is query-friendly and browsable.
  • Access: MinIO is S3-compatible. Point your S3 client at the MinIO endpoint_url with the MinIO access and secret keys.

Tech stack and prerequisites

  • Docker and Docker Compose
  • Python 3.11+, Apache Airflow 2.x
  • MinIO (server + console)
  • pandas, pyarrow, PyYAML, and an S3 client (minio / boto3 / s3fs)
  • Your own Git repository (the same one as stage 1)

Getting started

  1. Reuse the stage 1 dataset; place the CSV at dags/extraction/sample.csv.
  2. Story 1: write manifest.yaml and schema_contract.yaml.
  3. Story 2: write docker-compose.yaml (Airflow + MinIO); bring it up and confirm the bucket exists.
  4. Story 3: write the DAG; run it until partitioned Parquet appears in MinIO.
  5. Verify in the MinIO console, write the README, and open a PR for review.

Conventions: no secrets in code (use .env / Airflow Connections), catchup=False, and no heavy top-level I/O in the DAG file.

Stage 3 · Data warehouse · Requires: stages 1–2

Streaming and Batch Pipelines into a ClickHouse Medallion Warehouse

Objective

Find two public data sources, one realtime and one batch, and build a pipeline for each. Both pipelines load into ClickHouse using ELT to create a Medallion Architecture.

Requirements

Realtime / streaming source

  • A public data source that produces data continuously.
  • The pipeline is built with Apache NiFi.
  • Lands in ClickHouse through ELT into the medallion layers.

Batch source

  • A public data source that is pulled in batches.
  • The pipeline is built with Airflow + dbt.
  • Lands in ClickHouse through ELT into the medallion layers.

Key terms

  • ELT (Extract, Load, Transform): load the raw data into ClickHouse first, then transform it inside the warehouse. In ETL, by contrast, the data is transformed before it is loaded.
  • Medallion Architecture: data moves through three layers inside the warehouse: bronze (raw, as ingested) → silver (cleaned and conformed) → gold (business-ready aggregates and models).

Stage 5 · Analytics · Requires: stages 3–4

Dashboards with Apache Superset

Objective

Install Apache Superset with the ClickHouse driver included, then build an insightful dashboard on the data warehouse you created.

Steps

  1. Install Apache Superset with the ClickHouse driver included.
  2. Connect Superset to your ClickHouse data warehouse.
  3. Build an insightful dashboard from the warehouse.
  4. Power the charts with ClickHouse-specific analytical queries (see below).

Use what makes ClickHouse different

I expect your dashboard queries to use ClickHouse's own analytical features: functions and SQL clauses that a typical relational database such as PostgreSQL does not have. A dashboard you could have built on any database misses the point of this stage. Some places to start:

  • argMax / argMin: the value of one column at the row where another column is highest or lowest.
  • Aggregate combinators such as -If, -Array and -State / -Merge (e.g. sumIf, uniqIf).
  • uniq and quantiles: fast approximate distinct counts and percentiles.
  • windowFunnel, retention, sequenceMatch: funnel and cohort analysis in one query.
  • ORDER BY … WITH FILL: fill gaps in time series. LIMIT n BY: top-N per group.
  • ASOF JOIN: join each row to the closest earlier row in time.

Visual decisions (chart types, layout, which metrics to highlight) are up to you.

Stage 6 · AI · Requires: stages 3–5

A RAG System over the Data Warehouse

Setup

  1. Install the vector database Qdrant.
  2. Install the local LLM wrapper Ollama, and pull a lightweight LLM model.
  3. Create a new folder inside the same directory as your data warehouse mini project for the RAG system.

Core requirements

1. FastAPI app, backend only

Build a FastAPI-based app with no UI. It will be tested through the backend only.

It provides an endpoint that accepts a question, for example:

"What are the differences between the weather in Q1 and Q3?"

and returns the answer in the response of that same endpoint.

2. Embedding job: scheduled and on demand

An embedding job processes structured data from the data warehouse into NoSQL data in the Qdrant vector database, which becomes the knowledge source for RAG.

  • Scheduled: runs twice a day.
  • On demand: runs when an endpoint is called.

3. LLM calls

LLM calls are used to understand the user input and to generate the answer.

4. Guardrails: never hallucinate

The generated response must use proper guardrails and must never hallucinate. Test this with the question:

"tell me the recipe of chocolate pancake"

The answer must not come from outside the warehouse knowledge. A recipe is not in your data, so the system must decline rather than invent one.
